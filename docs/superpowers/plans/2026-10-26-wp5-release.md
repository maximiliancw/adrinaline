# WP5 Release: CI, PyPI publishing, README, dogfooding — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `adrinaline` 0.1.0: CI on Ubuntu and macOS, tag-driven PyPI publishing, a README that gets humans and agents started, and this repository's own decisions recorded with `adr`.

**Architecture:** Two GitHub Actions workflows (`ci.yml`, `release.yml`) using `uv`; README and `AGENTS.md` at the repository root; ADRs in `docs/adr/` created with the tool itself.

**Tech Stack:** GitHub Actions, `astral-sh/setup-uv`, `uv build`, `uv publish` (trusted publishing).

**Spec:** `docs/SPEC.md` (§3 packaging, §12 agent hint, §15 CI). Requires WP1–WP4.

## Global Constraints

- CI runs `ruff check`, `ruff format --check`, `ty check` and `pytest` on `ubuntu-latest` and `macos-latest` with Python 3.14.
- A pushed tag `v*` builds and publishes to PyPI via trusted publishing; the tag must equal `v` + the version in `pyproject.toml`.
- Action versions: use the latest major release of each action at implementation time (check each action's GitHub releases page; the versions below are placeholders to verify).
- Docs are agent-neutral and contain no hand-written dates. English; no AI attribution; Conventional Commits.

## Review Focus

1. The release workflow must refuse to publish when the tag and `pyproject.toml` version differ → check in Task 1, Step 3.
2. The built wheel must contain `adrinaline/data/*.md` (template, 0001, SKILL.md); a missing data file breaks `adr init` only after installation → test in Task 1, Step 2.
3. README commands must actually work as written → Task 2, Step 2 runs them.
4. `adr check --strict` must pass on this repository's own ADRs → Task 3, Step 3.
5. CI must not depend on the developer's global git config (`includeIf`, signing) → covered by `GIT_CONFIG_GLOBAL=/dev/null` in `tests/conftest.py`; confirm the first CI run is green.

```python
import subprocess
import zipfile
from pathlib import Path

ROOT = Path(__file__).parent.parent


def test_wheel_contains_data_files(tmp_path):
    subprocess.run(["uv", "build", "--wheel", "--out-dir", str(tmp_path)], cwd=ROOT, check=True, capture_output=True)
    wheel = next(tmp_path.glob("adrinaline-*.whl"))
    names = set(zipfile.ZipFile(wheel).namelist())
    for data in ("template.md", "0001.md", "SKILL.md"):
        assert f"adrinaline/data/{data}" in names
```

- [ ] **Step 3: Write the workflows**

`.github/workflows/ci.yml`:

```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v5
      - uses: astral-sh/setup-uv@v7
      - run: uv sync --locked
      - run: uv run ruff check
      - run: uv run ruff format --check
      - run: uv run ty check
      - run: uv run pytest -q
```

`.github/workflows/release.yml`:

```yaml
name: release

on:
  push:
    tags: ["v*"]

jobs:
  pypi:
    runs-on: ubuntu-latest
    environment: pypi
    permissions:
      id-token: write
    steps:
      - uses: actions/checkout@v5
      - uses: astral-sh/setup-uv@v7
      - name: Tag matches version
        run: test "v$(uv version --short)" = "$GITHUB_REF_NAME"
      - run: uv sync --locked
      - run: uv run pytest -q
      - run: uv build
      - run: uv publish
```

- [ ] **Step 1: Write `README.md`**

````markdown
# adrinaline

ADRs in a line: git-native Architecture Decision Records for humans and coding agents.

`adr` keeps decisions as Markdown files with YAML frontmatter in your repository, numbers them sequentially, links them into a graph, ties them to the code they govern, and answers every question in plain text or JSON.

## Install

```bash
uv tool install adrinaline   # provides `adr` (and `adrinaline`)
# or run without installing:
uvx adrinaline --help
```

Requires Python 3.14+ and git.

## Quick start

```bash
adr init                                   # docs/adr/.template.md + 0001-record-architecture-decisions.md
adr new "Use PostgreSQL" --tag storage     # docs/adr/0002-use-postgresql.md (proposed)
adr accept 2
adr new "Use PostgreSQL 17" --supersedes 2 --accepted
adr list
adr graph --format mermaid                 # paste into any GitHub/GitLab Markdown file
adr check                                  # CI-friendly validation
```

## Tie decisions to code

Add `scope` globs to an ADR's frontmatter:

```yaml
scope: ["src/db/**", "migrations/**"]
```

Then:

```bash
adr for src/db/pool.py                     # which decisions govern this file?
adr check --diff origin/main --strict      # CI gate: changed files governed by ADRs in force
```

## History

Every read command accepts `--at REF`:

```bash
adr list --at v1.2 --status accepted       # what was in force at release 1.2?
adr log 7                                  # git history of ADR 0007
```

## For coding agents

Add one line to `AGENTS.md` (or your agent's equivalent):

```markdown
Run `adr prime` at the start of every session and follow the ADRs it lists.
```

`adr prime --budget 400` limits the briefing to about 400 words, picking the most important and most relevant decisions first. `adr skill > .claude/skills/adr/SKILL.md` (or your agent's skill directory) installs a skill that teaches agents when and how to write ADRs. Every command accepts `--json` and returns a stable error envelope with exit code 3 on domain errors.

## Commands

| Command | Purpose |
|---|---|
| `adr init` | Create the ADR directory, template and ADR 0001 |
| `adr new TITLE` | Create an ADR (`--supersedes`, `--amends`, `--depends-on`, `--relates-to`, `--body-file -`) |
| `adr show REF` / `adr list` / `adr index` | Read ADRs |
| `adr accept` / `reject` / `deprecate` / `supersede` | Change status |
| `adr link` / `unlink` | Manage relations |
| `adr graph [REF]` | Text, Mermaid, DOT or JSON graph; `--reverse` for impact, `--rank` for keystones |
| `adr for PATH` | ADRs governing a file |
| `adr check` | Validate everything |
| `adr renumber REF --to N` | Fix numbering collisions after merges |
| `adr log REF` | Git history of an ADR |
| `adr prime` / `adr skill` | Agent briefing and skill |

The full specification is in [docs/SPEC.md](docs/SPEC.md).

## Licence

MIT
````

### Task 3: Record this project's decisions with `adr`

**Files:**
- Create: `docs/adr/.template.md`, `docs/adr/0001-record-architecture-decisions.md`, `docs/adr/0002-…` to `0005-…`

- [ ] **Step 1: Initialise and write the ADRs**

Run from the repository root:

```bash
uv run adr init
uv run adr new "Python with argparse, pydantic and ruamel.yaml" --accepted --body-file - <<'EOF'
## Context and Problem Statement

The maintainer reviews all code and has no Go experience. A single binary is desirable but not required.

## Considered Options

* Python 3.14 with uv, argparse, pydantic, ruamel.yaml
* TypeScript compiled with Bun
* Go

## Decision Outcome

Chosen option: "Python 3.14 with uv, argparse, pydantic, ruamel.yaml", because it is the easiest to review and distribute via `uv tool install`.

### Consequences

* Good, because round-trip YAML keeps hand edits intact.
* Bad, because there is no standalone binary in v1.
EOF
uv run adr new "Store only forward relations plus superseded-by" --accepted --body-file - <<'EOF'
## Context and Problem Statement

Relations between ADRs can be stored on both files or derived from one side.

## Considered Options

* Both sides on disk
* Forward relations only, plus `superseded-by`
* Forward relations only

## Decision Outcome

Chosen option: "Forward relations only, plus `superseded-by`", because the in-memory graph derives inverses, old ADRs stay untouched (fewer merge conflicts), and readers of a superseded ADR still see its successor.

### Consequences

* Good, because adding a relation changes one file.
* Bad, because `amended-by` and `dependency-of` are visible only through `adr`.
EOF
uv run adr new "Read-only git integration" --accepted --body-file - <<'EOF'
## Context and Problem Statement

`adr` needs git for the repository root, cross-branch numbering, history and diffs. Committing on the user's behalf would conflict with their own commit workflow.

## Considered Options

* Read-only git
* Optional `--commit`
* No git

## Decision Outcome

Chosen option: "Read-only git", because users and their agents stay in charge of every commit; a test guards against any git write.

### Consequences

* Good, because `adr` never surprises anyone with commits or fetches.
* Bad, because number allocation only sees refs as fresh as the last fetch.
EOF
uv run adr new "CLI as the agent interface" --accepted --body-file - <<'EOF'
## Context and Problem Statement

Coding agents need to read and write ADRs reliably.

## Considered Options

* CLI with `--json`, `adr prime` and a bundled skill
* An MCP server

## Decision Outcome

Chosen option: "CLI with `--json`, `adr prime` and a bundled skill", because every agent can run shell commands, and JSON output plus stable error codes make the CLI machine-friendly without another server.

### Consequences

* Good, because there is one interface to test and document.
* Bad, because agents without shell access cannot use `adr`.
EOF
uv run adr link 3 depends-on 2
uv run adr link 5 depends-on 2
```
